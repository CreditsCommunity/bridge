# Security review of the bridge specification

Date: 2026-11-06
Reviewer: security review agent
Reviewed: `docs/spec.md`, branch `docs/spec`, commit 7ae092a (first draft)

---

Read in full (934 lines). Runtime claims were checked against the CreditsCommunity node, contract-executor and smart-contract-api checkouts under the scratchpad `ref/` directory and against `probes/`. No files were edited.

## Summary verdict

The architecture is sound in its basic shape (threshold approvals on Credits, EIP-712 threshold claims on BSC, sequential ids, finalized reads, proof-based slashing) and most runtime facts in §13.1 are supported by the source. The draft is **not ready to implement**. Three problems are critical: (1) the slashing path can be switched off by any single relayer because proofs are blocked while paused while bond withdrawals are not; (2) the economic bound "vault cap ≤ bonds of the smallest T-coalition" does not hold, because cUSDT and USDT bonds cost a successful thief nothing and CS bonds can be withdrawn by a coalition that never lets the vault remove its keys; (3) a non-upgradable contract with unbounded state (withdrawal records, dust orders, pending approvals) will eventually exceed the per-node executor timeout (4 s default) and brick itself with all cUSDT inside. Several high findings concern liveness that a single relayer can break (conflict rule, pause), damage limits that are described as binding a colluding threshold but do not, and a migration path that can strand funds.

## Findings in detail

### C1. Proofs blocked while paused, bond withdrawal not (critical)
§8.9 lists what stays open while paused: "cancels, `claimCs`, `setReturn` and bond withdrawals that are due". `proveFalseSignature` is not in the list, so it is closed. Scenario: a coalition member pauses Credits (any single relayer, immediate), the coalition signs false claims and the vault pays them (or they are queued; T can unpause the vault); honest relayers cannot submit proofs; the colluders call `leave()` (or already did), wait 30 days, and `withdrawBond()` while still paused since "bond withdrawals that are due remain open" and "not under an open proof" is trivially true. Unpause needs T approvals, which the coalition withholds. Slashing, the only cost of the attack, never fires. Fix: `proveFalseSignature` MUST be callable in every state (paused, blocked, migration); `withdrawBond` and `leave` MUST be refused while paused; a pause started by relayer X should also extend X's own bond lock; and proofs must be accepted for a bond for as long as the bond is held (see M1).

### C2. Bonds do not bind a colluding threshold (critical)
§3.3 and §11 bound the loss by "vault cap ≤ bonds of the smallest T-coalition × conservative price". Three gaps void it. (a) cUSDT bonds: the thief deposited USDT to mint the bond; after draining the vault through false claims the same USDT is back in their hands, so the slashed cUSDT cost nothing (§3.3(4) says "it still costs the thief"; it does not). (b) USDT bonds on the vault: `bond(action 1 release)` needs only T signatures, so the coalition releases its own 50 USDT bonds before the theft. (c) CS bonds: `withdrawBond` requires only `leave()` + 30 days on Credits. The vault's signer set changes only through `updateSigners` signed by T of the current vault set, i.e. the leavers themselves, who simply never sign. Result: they are `Exited` on Credits (immune to proofs per §8.8 step 2), bond-free, and still valid signers on the vault. Fix: count only CS held by the contract toward the bond requirement and the cap bound; release a CS bond only after T of the *remaining* active relayers attest that a vault `SignerSet` without this signer has been applied (the attested vault signer-set nonce must be ≥ the nonce at which the relayer left); keep `Exited` relayers provable until that attestation; make USDT bond release follow the same attestation; drop cUSDT as bond collateral or weight it at zero.

### C3. Unbounded state will brick the contract (critical)
Facts from the source: the node waits `executor_receive_timeout`, default 4000 ms, per node (`client/config/config.hpp:113`), not the 60 s `Consensus::TimeSmartContract`; the executor serialises and deserialises the whole contract object every call; states above `Consensus::MaxContractStateSizeToSync = 8192` bytes are not carried in blocks, every node must re-execute or fetch them (`solver/src/consensus.cpp:116`). Growth sources in the spec: `withdrawals` one record per id forever (§14.2 open); asks/bids with no minimum size (0.000001 CS asks at ≈0.0175 CS each); `pendingMints` entries for any `depositId` a single relayer invents (no upper bound on the id); `mintedAbove` grows with every deposit above a permanently conflicted id (H1); `csClaimable` and per-epoch delegator lists (64 relayers × 100 entries per epoch). Once a call's deserialise + execute + serialise exceeds the slowest node's timeout, every call fails, state is unchanged, and the contract cannot be upgraded: all cUSDT is frozen and I1 breaks for everyone. Fix: minimum order size (≥ 1 CS and ≥ 0.01 cUSDT), per-wallet and global open-order limits; `approveMint` accepts only `depositId < attestedNextDepositId + window`; lazy expiry of `pendingMints` after N days; cap `mintedAbove` (refuse approvals more than K ids above the lowest unminted id); prune claimed withdrawal records on T-attested claim lists but keep a Merkle root of pruned records so proofs remain possible; measure deserialise time at the §12.1 scale (100,000 records) before freezing the design; state the maximum state size as a hard invariant.

### H1. One relayer blocks any mint (high)
§5.4: the first approval fixes the data; any differing approval sets `conflict`, after which the id is refused ("not in conflict") and only a 7-day vote can replace the data. `BridgeProbe.approveMint` implements exactly this. One malicious or buggy relayer picks a deposit and approves wrong data first (or second); the user's USDT is locked for at least 7 days; it can do this for 3 deposits per 7 days without even becoming `Inactive`, and `Inactive` is reversible. Every blocked id also leaves a hole under which `mintedAbove` grows (C3). The resolution vote lets a majority mint arbitrary data, a path weaker than "identical computed data". Fix: count approvals per data hash; mint when any hash reaches T from active relayers; approvals for a different hash only mark the approver (orphan counter); a true conflict exists only if two hashes both reach T, which the threshold rule should make impossible (drop the cap of 7 or make the cap ≥ N/2 + 1 for mints); approvals from relayers slashed or inactive before the T-th approval do not count.

### H2. Unlimited single-relayer pause (high)
Any relayer pauses both chains immediately; unpause needs T on each chain; nothing prevents the same relayer pausing again a minute later, and there is no consequence (no proof possible). While paused, `burnForBsc` and `claim` are both closed, so one newly admitted relayer with the minimum bond freezes every user's funds indefinitely. Fix: one pause per relayer per 7 days (enforced on both chains with the pauser's identity); after an unpause the pauser cannot pause for 30 days; a pause that T declares unfounded (an `Unpause` message with a flag) marks the pauser `Inactive` and extends its bond lock; consider answering §14.3 with "claims below the delay threshold continue during a single-relayer pause".

### H3. Damage limits do not bind T (high)
§3.3(1) says loss is limited by the daily cap, the 24-h delay, slashing and pause. In the text: `Cap` carries `dailyCap` and only `cap` increases are delayed, so T sets `dailyCap = cap` immediately; the delay is per claim, and the vault does not check Credits, so T signs many claims ≤ 1,000 USDT with unused ids; a single-signer pause is lifted by T `Unpause`; founders control the whitelist. The effective bound is the vault cap only, and slashing only if C1/C2 are fixed. Fix: delay `dailyCap` increases 7 days and cap them (e.g. ≤ 20 % of `cap`); apply the delay to the cumulative amount per UTC day (or per recipient per day) above the threshold, not per claim; require more than T for `Unpause` (e.g. `max(T, ceil(2N/3))`) and document the resulting stand-off; rewrite §3.3(1) to state the real bound.

### H4. 20,000 USDT limit tied to `foundersFrozen` (high)
`setCap`: "While not `foundersFrozen`: cap ≤ 20,000". `freezeFounders` is a flag in a `SignerSet` message signed by T, i.e. by the founders during the founder phase. They can freeze at any time and then double the cap every 7 days with no upper bound the vault can check (the "bonds × conservative price" rule exists only on Credits, where the same coalition votes). Meanwhile Credits closes its founder phase by a trade rule/6 months/7 relayers, unrelated to the vault flag, and the trade rule (a 100 cUSDT buy between "distinct wallets") is satisfied by one person with two wallets. Fix: let the vault compute the condition itself: `cap ≤ 20,000` while the number of founders in the signer set is ≥ `threshold()` (founders can reach T alone); remove the dependency on `foundersFrozen`; define one founder-phase end used by both chains.

### H5. Entry bond price (high)
§5.10: `entryPrice = max(conservativePrice, 7-day average)`. A higher cUSDT-per-CS price means fewer CS satisfy `bondCs × entryPrice ≥ requirement`, so a candidate who wash-trades for 7 days (cost: 0.1 % taker fee on the wash volume against their own asks) enters with a near-worthless bond; §9 says self-trades "only make entry dearer", which is backwards. Since the requirement is "fixed at entry", the coalition bound is permanently broken and cap proposals checked against bonds at conservative price will be computed on inflated entries. Fix: `entryPrice = min(conservativePrice, 7-day volume-weighted average)` or the conservative price alone; value all bonds at the current conservative price whenever a cap is proposed or executed; re-check I-style bound continuously, not only at proposal.

### H6. Lost deposits around the permanent block (high)
Credits sets `blocked = true` "at once" at vote execution and `approveMint` then requires `depositId < lastBscDepositIdAtBlock`; the vault refuses deposits only after `Block` lands, which needs T signatures and a BSC transaction. The spec never says how `lastBscDepositIdAtBlock` is obtained. If it is fixed at the Credits execution (the only time the contract has), every deposit accepted by the vault in the window is never minted and cannot be claimed back: user USDT lost. Fix: `lastBscDepositIdAtBlock` is set only by T relayer attestations of the vault's recorded `nextDepositId` after `Block`; until attested, mints are not restricted by the block; add an invariant "every deposit id below the vault's block id is mintable".

### H7. Migration liveness trap (high)
`migrate` burns cUSDT and records a `kind 1` withdrawal whose only valid recipient is `migrationTarget`; the claim reverts if the new vault reverts (cap, paused, withdrawOnly, bug) and "stays claimable", but it can never be claimed to the user. If the new system dies, the user has neither cUSDT nor USDT. Separately, relayers are bound for 12 months after the block; after that bonds unlock and relayers leave, and `withdrawOnly` is forever, so holders who did not withdraw within 12 months (and anyone whose relayers drop below T) are stranded, contradicting goal 5 and I12. Fix: the `migrate` record (and signed `Claim`) carries the user's own BSC fallback address; the vault pays `kind 1` to the target, or, after N days unexecuted (or if `migrationTarget` is unset/paused), to the fallback as a `kind 0`; alternatively do not burn on `migrate` until the new contract's credit is attested. For the end-of-life: bonds stay locked while any unpaid withdrawal exists for that relayer's active period (bounded by a long horizon), or define an explicit terminal procedure (e.g. after 12 months the vault threshold falls to the number of remaining signers with a 30-day queue on every claim).

### H8. Buyback drains the fee fund (high)
`closeEpoch` "buys CS from the lowest asks with the whole fund (no price limit)" and anyone may call it. Just before epoch end an attacker buys up the cheap asks, leaves one ask at an extreme price, and calls `closeEpoch`: the whole accumulated cUSDT fund buys dust CS from the attacker. Relayers themselves are best placed to do this. Fix: buyback at most `lastPrice`/7-day TWAP × 1.1 (or ≤ conservative price × k), spread over the epoch (at most X cUSDT per call, per hour), carry the rest over; or pay cUSDT directly to the reward ledger (the §2.2 "rejected alternative" is safer than an unlimited market order).

### M1. Rotated/exited keys not provable (medium)
`rotateSigner`: old key stays valid on the vault until the update lands; `relayerBySigner` is an index, so a false signature by the old key no longer resolves to a relayer. `leave` + `Exited` similarly. Fix: keep every signer key a relayer ever registered with its validity interval; accept proofs for any of them while the bond is held; reject `bscSigner` values already used by any relayer, past or present.

### M2. Honest slashing after a Credits reorg (medium)
Relayers sign at 3 blocks deep (§7.4). The node has an anti-fork mode and `uncertainBlock` alarms, i.e. reorganisations deeper than 3 are possible. If a `burnForBsc` is dropped by a reorg after signing, the signature becomes provably false (`id ≥ nextWithdrawalId` or a different hash): honest relayers lose bonds and, if the claim was paid, I1 breaks (cUSDT never burned). Fix: choose a depth from measured Credits reorg data and make it a parameter; do not sign while the node reports an uncertain/fork state; give proofs a grace rule (a signature over a record that existed at some height is not false unless the relayer also signed a conflicting record), or require proofs to cite the Credits block that contradicts the signature.

### M3. Conversion at mint in a thin book (medium)
Default `maxCsPrice = 0` (no limit, used in §8.1). With `conversionMin = 1` cUSDT, a 5 USDT deposit converts 1 cUSDT (20 %) at any price; larger deposits up to 20 cUSDT. A single ask at 100× market when the book is empty captures it from every depositor using the default. Fix: when `maxCsPrice = 0`, use `min(lastPrice × 2, conservativePrice × k)`; skip the conversion if the best ask is above that; drop `conversionMin` below 1 for small deposits (budget = 2 % only).

### M4. Daily cap griefing (medium)
A user round-trips 5,000 USDT (fee 0.1 USDT + gas) each day and consumes the daily cap first; all other claims revert that day. Fix: daily cap counts only claims above the delay threshold, or per-recipient daily limit, or a FIFO queue that preserves order instead of reverting.

### M5. Governance timing (medium)
§5.4 `execute`: "within 14 days, and 7 days elapsed since passing"; §8.7: "votes run 14 days ... applies 7 days after passing". A proposal passing on day 10 cannot execute within 14 days. "Passing" is undefined because votes are changeable and N changes. Fix: `votingEnd = created + 14 d`; `passedAt` recorded lazily when yes > N/2 first holds; executable in `[max(passedAt, votingEnd) + 7 d, +21 d]` with the pass condition re-checked at execution; state what happens to `N` changes mid-vote.

### M6. One-third veto (medium)
`objectApplication`: one third of active relayers (2 of 5) reject any applicant and the bond is returned. Incumbents can keep N small so founders keep T. Fix: remove the objection (the answer to §14.8), or let it only trigger a re-attestation of eligibility, or require a majority with the objection recorded publicly and a cost.

### M7. Non-deterministic digests and attestations (medium)
Digests include `userUsdt`, `totalSupply`, `unpaidWithdrawals` "per period" but Credits getters read the current state only (no historical reads: `getBalance` is current, §13.1; getters run on the latest state) and BSC values move continuously. Honest relayers will produce different digests and collect divergence marks (3 in 24 h → `Inactive`), and a T-coalition can post a common false digest to expel honest relayers in 3 hours, which also removes their ability to pause. `attestEligibility` requires T *identical* delegator lists of up to 100 entries that change whenever anyone delegates ≥ 5 CS. Fix: the contract snapshots its own values at the first call of each period (`totalSupply`, `nextWithdrawalId`, signer-set nonce) and relayers digest BSC values at the finalized block with the greatest timestamp ≤ period start; eligibility is decided by T attestations of the boolean plus the period tag, with the reward list taken as the intersection or the list of the median attestation; `Inactive` from divergence should keep pause rights and should not change the vault set for 7 days.

### M8. Emitted transfers are paid by the caller and can fail the call (medium)
Verified in `solver/src/smartcontracts.cpp` `prevalidate`: the start transaction's `max_fee` must cover the new-state min fee plus `getFee` of every emitted transaction, else the result is rejected and the state is left unchanged (`InsufficientMaxFee`); `walletscache.cpp` `smartSourceTransactionReleased` charges the initiator. The T-th `approveMint` therefore pays the CS transfer to the depositor and must set a sufficient `max_fee`; a relayer client using the minimum fee makes every mint fail. Emitted transfers to a contract address are violations (`SourceIsContract`) checked at block validation, so a mint whose `to` is a contract (or a `buy` whose return address is a contract) fails as a whole. Fix: never emit CS inside the mint; credit `csClaimable[to]` and let the user pull; specify relayer `max_fee`; document that the caller pays emitted fees (this closes §13.2.3).

### M9. `depositFromMigration` (medium)
The text says the old vault "approves the target and calls `depositFromMigration(amount, creditsTo)`". The new vault must restrict the caller to the registered old vault and pull the USDT with `transferFrom` measuring the balance delta; otherwise anyone can create unbacked deposits on the new system. Fix: state it as a MUST in §6.3.

### M10. Founder-phase arithmetic (medium)
With F founders, founders reach T alone while F ≥ T, i.e. N ≤ 2F − 1 (F=5 → up to 9 relayers, F=3 → up to 5), not "until there are 8 relayers". §11 ends the founder phase at 7 relayers, when 5 founders still reach T=4. Fix: define the condition as "founders in the active set ≥ T" everywhere (also H4).

### L1–L9 (low)
L1: `double` guarantees 15 significant digits; 10⁹ CS with 6 decimals needs 16; cap single emitted transfers at 10⁸ CS or check `BigDecimal.valueOf(d) ≤ intended` and subtract one unit otherwise. L2: fix the Rejected-applicant lock text. L3: require `minWithdrawal > bridgeFee + minClaim`. L4: use a rolling 24-h window. L5: label the "3 relayers" rule as operational or implement it in the vault (`threshold()`-based). L6: nonce-bind `Pause` to a short expiry; remove `Bond(action 0)` or specify it. L7: allow immediate admission of a version when signed by T plus majority, with the old version retired after grace. L8: `Consensus::stakingOn = false` (`solver/src/consensus.cpp`) with a warning comment; verify on mainnet whether 1-year delegations earn anything, otherwise the eligibility rule has no reward and may starve relayer supply. L9: release the 50 USDT by the same attestation as the CS bond (C2) rather than a discretionary signature.

## Underspecified items an implementer would have to guess

1. Exact EIP-712 type strings, and the Java encoding of `hashStruct(Claim)` (uint64/uint8 padding, address padding, `amountWei = units × 10¹⁰` as uint256, `creditsTo` bytes), plus the address normalisation (lowercase hex) used in the record, the relayer signature and the proof.
2. How `lastBscDepositIdAtBlock` and `userUsdtInVault` reach the contract (attestation message, who submits, T rule).
3. Signer-set history per nonce on Credits so relayers can rebuild every intermediate `SignerSet` message; what happens when several nonces advance before one lands; whether `Inactive` changes the set immediately.
4. Which methods are open in `paused`, `blocked` and `migration` states (`leave`, `withdrawBond`, `proveFalseSignature`, `vote`, `execute`, `attestEligibility`, `submitDigest`, `closeEpoch`, `placeBid`, `cancelBid`).
5. Whether approvals from relayers that become `Inactive`/`Slashed`/`Exiting` between their approval and the T-th still count; whether `T` is evaluated at each approval or at the T-th.
6. `participation` accounting: how post-mint approvals are recorded for 10 minutes, and what counts when no deposits occur in a window.
7. Snapshot rules for digests and delegator lists (M7); maximum attestation size; how often attestations are refreshed; what `eligible=false` by fewer than T means.
8. Order book details: tick size, minimum order, maximum open orders, behaviour of `buy` when `maxFillsPerCall` is hit mid-order (partial spend returned?), fee rounding when `qty × price` has more than 8 decimals, `lastPrice` definition (last fill or VWAP of the call), how `dailyVolume[7]` rolls.
9. `conservativePrice` default before any vote and what "Vault cap (after) ≤ bonds × conservative price" means if it is unset at phase end.
10. `withdrawBond` when `bondCusdt` is paid to a `Slashed`/`Exited` relayer's balance while blocked; what the slash reserve is used for (§14.1).
11. `payable` commands: parsing grammar (separator `|`, decimal format, address validation), maximum `userData` length, behaviour for `sell` with no bids.
12. Relayer: how to locate a `burnForBsc` transaction's block to measure depth; the `credits_confirmations` value justification; `max_fee` to set on `approveMint`, `buy` and `closeEpoch`.
13. BSC: behaviour of `claim` when `dailyCap` is exceeded (revert vs queue); `executeQueued` by anyone paying gas (incentive); whether `kind 1` queued claims are also delayed.
14. Address of `creditsTo` validation on the vault (any non-zero bytes32 is accepted; a contract address or invalid key makes the mint target unspendable: the contract should credit a `csClaimable`/balance rather than emit).
15. Initial relayer set bootstrap on Credits (who calls the first `applyRelayer`/`activate` when N=0 and T=2 cannot be met) and the vault constructor's initial signers must match it.

## Checked and found sound (with evidence)

- `getBlockchainTimeMills()` is the block time of the block containing the start transaction: `api/src/executor.cpp:463` passes `headTransaction.get_time()` (set from block time by `BlockChain::loadTransaction`/block reads, never serialised from the sender) and `generateAccessId` falls back to `BlockChain::getBlockTime(loadBlock(sequence))`; re-execution uses the explicit sequence, so §13.2.1 should hold.
- A `payable` that throws returns the CS to the sender: `walletscache.cpp` `invokeReplenishPayableContract` holds the amount until the new state; `checkSmartWaitingForMoney` → `rollbackExceededTimeoutContract` refunds `amount` (minus counted fee) when the new state is not updated. The "unattributed" fallback in §5.5 is unnecessary; keep the throw.
- Contract-emitted transfers carry no user data: `smartcontracts.cpp:2328` builds the emitted `csdb::Transaction` without any user field although the executor result carries `userData`.
- Contract → contract transfers and `@UsingContract` calls are violations (`SourceIsContract`, `SubsequentCall`, `smartcontracts.cpp:964-1016`); `MaxContractResultTransactions = 100` bounds emitted transfers per call (the spec never emits more than one per call).
- `TimeMoney` sets `coeff = Anni` for a term ≥ 4 × 7,862,400 s (≈ 364 days) computed from `validUntil − fromTime` (`csnode/src/nodecore.cpp`); enum value `Anni = 4` (`nodecore.hpp:154`). Timed delegations cannot be withdrawn before expiry: `itervalidator.cpp` `legated_withdraw` only matches records with `time == 0`. Delegation to a contract is refused (`kTransactionProhibited`). `MinStakeDelegated = 5` CS. The spec's "validUntil > now + 30 days" filter is right since `coeff` reflects the original term, not the remaining one.
- `executor_receive_timeout` default 4000 ms per node (`client/config/config.hpp:113`) versus `TimeSmartContract = 60000`; the executor itself enforces the 60 s with `Thread.stop` (`LimitedExecutionMethod.java`). The spec's "size work to stay below 1 s" is the right target; see C3 for the state-size dimension.
- Fee table: min fee 0.008740 CS per transaction below 5 KB, new state min fee the same, execution fee 1 min-fee per second (`csnode/src/fee.cpp`); the ≈0.0175 CS figure is consistent.
- Sandbox: contract classes get a fixed `Permissions` set (`PermissionsManager.java`); `BigDecimal`, `BigInteger`, `TreeMap`, `String.format` need no permission; `SigProbe` already runs under it (§12.1).
- `initiator` is the base58 of the caller's public key (`ExecuteByteCodeSession.java:59`); method parameters support `v_big_decimal` (`general.thrift`), and the executor passes the Text user field to `payable` as a byte array (`executor.cpp:440`).
