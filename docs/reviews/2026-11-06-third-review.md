# Security review of the changes since the re-review (spec `docs/spec` at 842b027, diff d1f33aa..docs/spec)

Read-only. Sources: `git show docs/spec:docs/spec.md` (1,788 lines), the two earlier reviews, and `git log -p d1f33aa..docs/spec -- docs/spec.md` (12 commits, +475/−111). Nothing was checked out, edited or committed. Line numbers refer to `git show docs/spec:docs/spec.md`.

## Verdict

The decisions D8–D14 and the smaller changes are implementable, but four of them open holes that must be closed before approval, and two of those are caused by the decision text itself rather than by an editing slip:

1. **D14 moves every power of the relayer onto the node wallet, which is a hot key on the server.** A server compromise now takes the operator's whole CS bond (100,000 CS for a founder, ≥ half the entry value for others) and all future rewards: the thief calls `leave()` and `setReturnAddress()`, both open to the node wallet alone. §3.2 and §9 say the theft "is the same as one malicious relayer"; it is not. This is operator-fund loss created by the decision. One signature field in `Bind` fixes it without reintroducing an operator wallet (F1).
2. **D12 + D14 vault bookkeeping is keyed on the wrong things.** `bondReturn` is fixed by whoever calls `depositBond` first, so a griefer with 1 wei of USDT can pre-claim any node wallet (including the three founders' at launch, from the vault constructor arguments) and permanently prevent the real relayer from bonding (F2). `bondSigner` is the key given at deposit, so after an ordinary `rotateSigner` the bond is attached to a removed key and the still-active relayer can `reclaimBond` it alone after 60 days, breaking I14/I21 (F3).
3. **D9 lets two relayers below `T` lock every user out for good when `N` is 4 or 5** (two pausers make a full pause; unpause needs `U = 3` of 4 or `4` of 5, which the two pausers can deny; a pause never expires). D2's guarantee "an honest pause never locks users out" no longer holds against a sub-threshold pair (F4).

The rest is Medium/Low: the exact-fee rule on deposits reverts users' deposits around the pool target and on any parameter change (F5); refunds to an arbitrary `msg.sender` go to MEV bots and make the relayers' own submissions revert (F6); the price band interacts badly with D1's unlimited automated purchases, because one 100-csUSDT wash fill per day both ratchets the reference by +20 % and prevents the anti-freeze decay, while honest asks below the floor are parked and no longer need sweeping (F7); the decay has no floor and only one direction (F8); the conservative price can never leave 0 under the "×2 per 7 days" rule as written (F9); the new non-blocking queue lets direct small claims starve a large queued claim indefinitely (F10); plus `reclaimBond` edge cases, a zero proof margin at depth 10, `vaultView.dailyCap` bootstrapping, and ~25 inconsistencies.

## Details

### F1 (High) — D14: a stolen server now costs the operator its CS bond and rewards
Text. §4.1 l.379: the node wallet "pays and recovers the CS bond; … receives the owner share of rewards"; it is "the node's own key, on the relayer server". §5.4 l.535: `setReturnAddress(addr)` is **W** (node wallet), immediate. §5.4 l.537: `leave()` is **W**. `withdrawBond()` credits `csClaimable[nodeWallet]`; `deliverCs` (anyone) sends it to `returnAddress(nodeWallet)`. §3.2 l.279 and §9 l.1304 state that theft of the server keys is "the same as one malicious relayer" and that only the BSC wallet is protected.
Scenario. An attacker copies the node wallet key (it must be on the server: it is the node's consensus key) and `bscSigner`. It calls `setReturnAddress(attacker)` and `leave()`. The honest relayers apply the signer set without this relayer; 30 days later anyone calls `withdrawBond()` then `deliverCs(nodeWallet)`: 100,000 CS (founder) go to the attacker. Meanwhile every epoch's owner share goes to the attacker too. The operator shares the key, so there is a block-level race on `setReturnAddress` at delivery time, which automation wins. Alternatively the attacker signs a false claim with `bscSigner` and proves it from a fresh wallet: the bond goes to the reserve and the attacker is the prover (10 %); an appeal "stolen key" that succeeds returns the bond to… the relayer's return address, i.e. the attacker. In revision 2 the hot operator key could do none of this (bond and return address belonged to the node wallet, which could be kept offline).
Why the text allows it. D14 removed the operator and owner wallets and made the node wallet the only Credits identity; nothing on Credits is signed by a key that is not on the server.
Fix (keeps D14's two wallets; no new Credits key). Put the CS destination under the cold BSC wallet, which already signs bindings: add `bytes32 csReturn` to `Bind` (`Bind(bytes32 nodeWallet,address bscWallet,address bscSigner,bytes32 csReturn,uint256 chainId,bytes32 creditsContract,uint64 nonce)`); the relayer's bond and rewards are credited to `csClaimable[csReturn]`, and `setReturnAddress` for a relayer's node wallet is replaced by `setRelayerReturn(csReturn, walletSig)` carrying a `Bind` signature of `bscWallet` with the next `bindNonce`. Optionally `leave()` also requires `walletSig` (then a thief can only get the relayer slashed, which is the "one malicious relayer" case; the appeal path then returns the bond to the cold address). Rewrite §3.2 and §9 to list exactly what a server thief can do (approve, sign, pause once, vote, get the relayer slashed) and cannot (move the CS bond, the USDT bond, the rewards' destination).

### F2 (High) — D12/D14: `depositBond` front-run fixes `bondReturn` to a stranger
Text. §6.3 l.903: "the first deposit fixes `bondReturn[nodeWallet] = msg.sender`…, later deposits must come from the same address"; no minimum amount; the vault cannot verify the binding (it never sees Credits). §5.8 `bscBond`: the depositing address "must be the bound `bscWallet`". §5.14 step 4: founders' node wallets are constructor arguments; the vault refuses user deposits while a founder in the set has `bondUsdt[founderWallet] < 50`.
Scenario (launch). The vault is deployed with the three founders' node wallets in its constructor arguments. A griefer calls `depositBond(founderNodeWallet, anyKey, 1 wei)` for each of them before the founders do (front-running the first `depositBond` in the mempool, or simply being first). `bondReturn` is the griefer; every founder's own deposit reverts; `bondUsdt[founderWallet]` stays at 1 wei; no user can deposit (N8 rule); 30 days later the founders become `Inactive` (§5.14 step 7), the vault falls below 3 signers, and the bridge is dead. Redeploying the vault repeats the race. Cost: gas plus 3 wei.
Scenario (later). Every Credits node's public key is public; the griefer pre-seeds `depositBond(nodeWallet, …, 1 wei)` for any node that might apply. That node wallet can never satisfy `bscBond` (the depositing address is not its `bscWallet`); the operator must create a new node identity and re-delegate 1M CS for a year.
Fix (keeps D12's fixed return address). Key the bond by the pair: `bondUsdt[nodeWallet][bscWallet]`, with `bondReturn` implicit (`= bscWallet`); `releaseBond`, `reclaimBond`, `slashBond` and `ReserveUse` take `(nodeWallet, bscWallet)` (add `address bscWallet` to `BondRelease`, `BondSlash` and `ReserveUse`). A stranger's deposit is then its own separate bond, returned to the stranger, and the Credits attestation names which pair is the relayer's. For the founders' N8 condition use the sum over wallets, or (better) take the founders' `bscWallet` in the constructor pairs `(signer, nodeWallet, bscWallet)` since they are known before deploy. Alternatively, keep a single bond but accept the first deposit only when it is ≥ 50 USDT and is accompanied by the `bscSigner`'s `Bind` signature over `(nodeWallet, msg.sender, bscSigner, …)`, which the vault can verify with `ecrecover`; that still leaves the pre-seeding race for amounts ≥ 50 USDT, so the pair-keyed ledger is the cleaner fix.

### F3 (High) — D12 × rotation: `bondSigner` is the old key after `rotateSigner`
Text. §6.3 l.903: `depositBond` "records `bondSigner`"; l.904–905: `releaseBond`/`reclaimBond` require "`bondSigner[nodeWallet]` not a signer and `removedAt + 30/60 days` passed". §5.4 l.536: `rotateSigner` records a new signer set; §6.3 `updateSigners` "sets `removedAt` for removed signers". Nothing updates `bondSigner` at rotation (the vault does not know which new key belongs to which `nodeWallet`: `SignerSet` carries only addresses).
Scenario. Relayer R deposits its bond with key K1, is activated, then rotates to K2 (its own `bscWallet` signs; nothing suspicious). `updateSigners` removes K1 (`removedAt[K1] = t`) and adds K2. From `t + 60 days` R calls `reclaimBond(nodeWallet)`: `bondSigner = K1` is not a signer, no slash, the whole USDT bond is paid to R's `bscWallet` while R is an active signer with K2. From `t + 30 days` the same works through `releaseBond` with `T` signatures (pre-existing wording, but it needed a coalition; `reclaimBond` makes it a solo move). A relayer planning a theft pre-extracts its USDT bond; an entrant keeps only the CS half of D8. For a founder the self-harm (N8 blocks deposits) limits it; for every later entrant it is free. I14 ("never released while its signer key is in the set") and I21 are false as written. User funds are not touched (USDT bonds never counted for the cap bound, C2), but D12's own guarantee and the entry requirement are void.
Fix. Make the vault track bonds by node wallet, not by key: add `bytes32[] nodeWallets` (parallel to `signers`) to the `SignerSet` type (§6.2) and to the Credits `signerSets` record; `updateSigners` keeps `signerOf[nodeWallet]` and sets `removedAt[nodeWallet]` only when the node wallet has **no** key left in the new set, clearing it when it is re-added; `releaseBond`/`reclaimBond` test `signerOf[nodeWallet] == 0 && removedAt[nodeWallet] + 30/60 days ≤ now`; drop `bondSigner`. Add a test "rotation, then reclaim refused while the new key is a signer" to §12.3.

### F4 (High) — D9: two relayers below `T` lock the bridge for good at `N` = 4 or 5
Text. §8.9 l.1251–1256: a second distinct pauser makes a full pause (small burns and claims stop); unpause needs `U = max(T, ceil(2N/3))` on both chains; a pause has no expiry (the `Pause` message's deadline bounds only its submission, l.1241). `leave`/`withdrawBond` are refused while paused (C1).
Arithmetic. Two pausers lock everything iff `N − 2 < U`: `N = 4`: `T = 3`, `U = 3`, honest 2 < 3; `N = 5`: `T = 3`, `U = 4`, honest 3 < 4. (`N = 3` is also locked but 2 = `T` there, inside the trust model; from `N = 6` the honest rest reaches `U`.)
Scenario. With 5 relayers (three founders plus two entrants, a likely state in the first months), the two entrants pause on both chains one after the other. Every withdrawal stops: `burnForBsc` closed, `claim` refused. The three honest relayers cannot reach `U = 4`; the "unfounded" penalty needs an unpause, so it never fires; the pausers cannot leave either, but neither can users. Goal 5 and I12 fail for a coalition below `T`; this is beyond the trust model (which only concedes a colluding `T`). Also: D2's single-level pause continues to pay small claims, so a theft in progress is not the reason to lock; a lock of honest users is the only effect a sub-threshold pair can obtain.
Fix (keeps D9). Give the full level an expiry: the full pause lasts at most `fullPauseMax` (e.g. 72 h, code) from the second pause and then falls back to the single-level pause of D2 unless a **third** distinct relayer renews it (each renewal counts as that relayer's one pause per 7 days); the automatic `mint-mismatch` full pause instead ends only by vote resolution, as today. On BSC the same expiry applies to `fullPause`. Also state the positive effect in §3.3(1): with `N = 5` or `N ≥ 7`, two honest relayers can now fully stop a `T`-coalition theft, because `T < U` there (see "Sound items").

### F5 (Medium) — D13: exact fee on `deposit`
Text. §6.3 l.896: "`msg.value` MUST equal `currentGasFee()` exactly (`gasFee`, or 0 while `gasPool ≥ gasPoolTarget`), else revert".
Scenario. The pool is at 0.0499 BNB; Alice's deposit (fee 0.0001) lands and the pool reaches the target; Bob's deposit, built a few seconds earlier with 0.0001, reverts; Carol's built with 0 after that reverts when a refund drops the pool below the target again. Any `setGasParams` (which needs `T` signatures and is refunded) makes every pending deposit revert. A griefer can flip the fee deliberately: submit a refundable update (e.g. a legitimately signed `Pause` or a pending `SignerSet`) right before a visible deposit. Users lose BSC gas and trust; no funds are lost.
Fix (keeps the fee and the target). Accept `currentGasFee() ≤ msg.value ≤ gasFee` (the voted fee, ≤ 0.001 BNB hard cap) and add all of it to the pool; the deposit page sends `gasFee` unless the pool is comfortably above the target (hysteresis, e.g. ≥ 1.5 × target) and then sends 0. Reverting only when `msg.value > gasFee` still protects against mistaken large transfers. Add the two edge cases to §12.3.

### F6 (Medium) — D13: refund recipient and refund measurement
Text. §6.3 l.923–934: the submitter (`msg.sender`) of the first state-changing submission is refunded `(gasleft at entry − gasleft at exit + 30,000) × min(tx.gasprice, maxRefundGasPrice)`, capped; sent "with a plain value transfer under the reentrancy guard"; a replayed nonce reverts. §7.6: relayers submit after a random 0–120 s delay.
Scenarios. (a) The signatures are in the calldata of the relayer's transaction; a bot copies it with a higher gas price and is refunded (it earns ≈ 30,000 × 3 gwei ≈ 0.0001 BNB above cost); the relayer's transaction reverts on the nonce and pays its gas with no refund. Over time no relayer submitter is ever refunded, their hot accounts run dry, and the pool pays bots at the full rate. The update itself is never at risk. (b) If gas is measured after the refund transfer, or the transfer forwards all gas, a contract receiver burns gas up to `maxRefundPerTx` on each call; if `transfer()` (2,300 gas) is used, a multisig operator wallet never gets a refund. (c) Refund arithmetic uses `gasleft at entry`, so the 21,000 base and calldata cost are only covered by the "+ 30,000" constant; `updateSigners` with 64 addresses has calldata above that.
Fix. Pay the refund only to a registered recipient: either `msg.sender == bondReturn[...]` of a current signer's node wallet (the vault already stores the relayers' BSC wallets), or a `submitter[address]` that a `bondReturn` wallet registers with a plain transaction (`setSubmitter`), or the claim page's user when the message carries `refundTo` signed by the signers (urgent messages only). A bot then gains nothing by front-running and has no reason to grief. Specify: measure `gasleft` **before** the refund call; forward a fixed stipend (e.g. 50,000 gas) with `call{value}`; update the hourly counter before the call (CEI); replace "+ 30,000" by "+ 21,000 + 16 × calldata bytes" or raise it. Keep "refund failure keeps the update".

### F7 (Medium) — D11 × D1: ratchet, hold, and cheaper capture of conversions and the buyback
Text. §5.9: `refPrice` = previous day's VWAP of fills ≥ 100 csUSDT; one fill qualifies; `idleDays` resets on any qualifying fill; orders below the floor are parked; §5.9 last bullet of the band and §5.7.1 step 3: conversion and buyback "keep no price limit of their own (D1)". §9 l.1320 claims "buyers then stop, and the anti-freeze decay brings it back".
Scenario (thin book, which is the opening situation). Day 1, `ref = 0.020`. The attacker places an ask at the ceiling 0.024 and buys it from a second wallet for 100 csUSDT (fee 0.10 csUSDT). Day 2 `ref = 0.024`; repeat at 0.0288; after 13 days `ref ≈ 0.20` (×10), after 26 days ×100. Honest asks placed at the old prices are below the floor and parked: they are never hit, by anyone. Every mint's conversion (up to 20 csUSDT, page default `maxCsPrice = 2 × lastPrice`, itself inflated) and every hourly buyback slice buy from the attacker's ask at the floor; the attacker no longer needs the N3 sweep-and-tick race, because the band parks the competition. To keep the price there it needs one 100-csUSDT fill per day; if honest sellers post asks at the inflated floor it must buy those first (lowest, oldest first), so the holding cost is at most ≈ 100 csUSDT per day and usually far less; in a deep book honest sellers get paid at the inflated price, which is the self-correcting part the spec relies on, but the losers are depositors and the reward fund, not the attacker. The decay never starts, so the §9 sentence is false. Depositors whose conversion finds only parked asks get csUSDT and no CS and cannot send any Credits transaction (pre-existing with an empty book, now more likely).
Why the text allows it. D11 bounds the daily step but not the direction over days, and D1 says automated purchases follow the market whatever it is; the band removes the honest undercutting below the floor that used to make a sweep necessary.
Fix (within D11; the last item touches D1 and is the owner's call). (1) Count a fill as qualifying only when taker and maker wallets differ (Sybil-able, but it doubles the attacker's wallet count and fees). (2) Make the upward step the same as the downward one (5 %, or 10 %) so a ×10 takes 47 days, not 13; `bandUp` 20 % only helps a manipulator, honest discovery upward is still 5 %/day. (3) Make `refPrice` for the day `min(VWAP, previous refPrice × (1 + bandUp))` **and** apply the decay also when the day's qualifying volume comes from fewer than two distinct taker wallets. (4) Say plainly in §3.3(8) and §9 that, with D1, conversions and the buyback can be captured by holding the band for ≤ 100 csUSDT/day; if the owner wants it closed, automated purchases must have a ceiling independent of the manipulable reference, e.g. `conservativePrice × 2` (vote-set), which is a change to D1.

### F8 (Medium) — D11: the decay has no floor and only goes down
Text. §5.9: after 3 idle days `refPrice` falls 5 % per further idle day "until a qualifying fill"; nothing stops it; "while it is 0 no order can be placed".
Scenario. The bridge is quiet for four months (common for a small bridge; also after a pause): 120 idle days → `ref × 0.95^117 ≈ ref / 400`. Trading resumes: nobody sells CS at 1/400 of its value; buyers who want to pay the real price cannot place a bid above 1.2 × ref; climbing back takes 33 days at +20 %/day (and the climb itself requires qualifying fills at each step, i.e. somebody selling at the depressed price). The conversion at mint buys nothing (all asks parked above the ceiling). Mirror image of the freeze the rule was meant to prevent.
Fix. Stop the decay at a floor tied to the vote-set value (e.g. `refPrice ≥ conservativePrice / 4`) or, better, make the anti-freeze **widen** the band instead of moving the reference: after `bandIdleDays`, `bandDown` and `bandUp` each grow by 5 points per idle day (to a cap), and the first qualifying day resets them. Widening does not assume which way the price was wrong.

### F9 (Medium) — the conservative price can never be set from 0
Text. §11 l.1392: "Conservative CS price: 0 until set by vote; lowering immediate, raising after 7 days, at most ×2 per 7 days". §5.9: "Opening: `refPrice = conservativePrice`; while it is 0 no order can be placed". §16.1 assumes 0.020 on day 1.
Consequence. `0 × 2 = 0`: no proposal can set a positive price under the rule as written; even with an exception for the first value, `propose` is only open in `Normal`, so the order book, every conversion at mint and I18 are dead for ≥ 21 days after the link (14-day vote + 7-day delay). §16.1 is therefore not possible as told.
Fix. Carry the initial conservative price in the `link` attestation (the founders already attest the vault address by a majority; the value is public and the deployer gains nothing), or exempt the first non-zero setting from the ×2 rule and let it pass as a bootstrap vote; say which in §5.9, §5.14 step 5, §11 and §16.1.

### F10 (Medium) — non-blocking queue starves large claims
Text. §6.3 `executeQueued` l.898: "a claim that does not fit yet keeps its place but does not block the later ones"; `claim` l.897 pays a fitting claim directly, bypassing the queue.
Scenario. Erin's 1,900 USDT claim is queued (cap 2,000). A griefer with 2,000 USDT round-trips it: deposit, burn in 4 × 500, claim each directly as soon as the window frees 500. The window never has 1,900 free; Erin waits as long as the griefer pays 0.1 csUSDT fee plus gas per cycle. Honest traffic alone produces the same effect at any sustained volume near the cap. A single-claim cap (`burnForBsc` ≤ `dailyCap`) guarantees the claim fits in an empty window, not that the window ever empties.
Fix. Reserve for the head of the queue: a direct `claim` and a later queued claim are paid only if `window + amount + (amount of the oldest unlocked queued claim) ≤ dailyCap`; equivalently, every `claim` first tries to pay the queue head. Keep the "lowered cap" exception.

### F11 (Low) — `reclaimBond` edge cases
(a) A key never in the set has `removedAt = 0`, so "`removedAt + 60 days` passed" is true at once: an applicant can reclaim its attested USDT bond at any time, including between the `bscBond` attestation and `activate` (the relayers attest "when it changes", but nothing requires a fresh attestation at `activate`). With D8 the harm is bounded (USDT never counts for the cap), but the entry requirement is not what the contract believes. (b) `Inactive` relayers are removed from the vault set and "return to `Active` with the same bond" (§8.6): a relayer can go inactive on purpose, reclaim after 60 days, and return without its USDT bond; nothing re-checks `bondUsdtOnBsc` on the way back. (c) `updateSigners` sets `removedAt` on removal but the text never clears it on re-adding. Fix: with the node-wallet keying of F3, require `removedAt[nodeWallet] > 0` for `reclaimBond` (never-signers get `releaseBond`, already stated for cancelled applicants) and clear it on re-add; on Credits, `activate` and the return from `Inactive` require a `bscBond` attestation not older than one digest period showing at least the USDT part the relayer had at entry (`max(50, R − bondCs × entryPrice)`), generalising the N8 founder rule.

### F12 (Low) — proof age equals signing depth
§7.4: sign at 10 blocks (≈ 13 s); §8.8 step 3: a signature is false when the stored record differs "and the stored record is older than `creditsConfirmations` blocks". A reorganisation of depth 11 that replaces a burn with another therefore slashes an honest relayer that followed the rule exactly; the only defence is the appeal and a two-thirds vote. The data behind 10 blocks is 100 block intervals and logs with no fork event; §13.2(5) admits it. The owner chose the depth; the proof margin is the spec's own choice and is free to widen: require the contradicting record to be older than `proofDepth = max(100, 10 × creditsConfirmations)` blocks, and keep the 64-id margin. Also state that the relayer refuses to sign when its node reports `uncertainBlock` within the last `proofDepth` blocks.

### F13 (Low) — `vaultView.dailyCap`
§5.1 adds `dailyCap` to `vaultView` and `burnForBsc` requires `net ≤ vaultView.dailyCap`, but the `vault` attestation payload (§5.8) does not carry `dailyCap`, and nothing gives it an initial value: before the first `T`-identical attestation no burn passes. Fix: add `dailyCap` (and `cap`) to the `vault` payload; take the initial values from the `link` attestation (the constructor arguments); while attestations are stale, use the last value (a lowered cap is already handled by `executeQueued`).

### F14 (Low) — I20 cannot be enforced
`selfdestruct` (still able to force value in the creating transaction after Cancun) puts BNB into the vault regardless of `receive` reverting. Say that `gasPool` is an internal counter, refunds are paid from it only, and `address(this).balance ≥ gasPool` is the invariant; forced BNB stays unreachable, which is harmless.

### F15 (Low) — D14/D12 notes
`Bind` is verified in Java with `ecrecover`-style recovery, so `bscWallet` must be an EOA (no EIP-1271 contract wallets): say so in §4.1 and in the operator guide. With `bondReturn` fixed for life, losing the BSC wallet key loses the USDT bond and all refunds with no recovery; this is the price of D12 and should be stated under §3.3 or §7.8, possibly with a `T`-signed, 30-day-delayed `changeBondReturn` that the owner may or may not want.

## Inconsistencies introduced or left by the edits

## Sound items (no change needed)

- **Bind message (D14)**: `nodeWallet`, `chainId`, `creditsContract` (the contract's own key) and `bindNonce` in the struct, a dedicated domain name without `verifyingContract`, and both `bscWallet` and `bscSigner` signing. No replay across relayers, contracts, redeploys or the vault's own domain; the signer's own signature closes the "register someone else's key to burn it under M1" squat; M1 blocks replay of an old `Bind` after a cancel-and-reapply.
- **Rotation requires the cold wallet's signature**: a server thief cannot rotate the signer, so it cannot outlive a key-change response by the operator.
- **D12 60-day `reclaimBond`**: closes N5's "bond stuck by withheld signatures" for the USDT part; the CS bond's 30-day window on Credits is shorter, so a proof that reaches the CS bond in time also reaches the USDT bond; the relayers' software signing `BondSlash` at once is the right default; the accepted residual (`T` withholding the slash for 60 days) is inside the trust model.
- **D13 refund design**: refund after the state change, under the reentrancy guard, failure non-reverting, per-call and per-hour caps, gas price capped, no refund for reverted or replayed calls, no refund on user paths, hard caps on all five parameters. Loops cannot drain the pool: every refunded message needs `T` signatures except `Pause` (one per signer per 7 days) and a founder's own `FounderRemoval` (once).
- **D8**: with `entryPrice = min(conservative, VWAP)` a wash trade in either direction cannot lower an entrant's CS requirement; the half-in-CS floor plus I18 at activation closes N1 as intended.
- **D9 as a bound on theft**: for `N = 5` and `N ≥ 7`, `T < U`, so two honest relayers can now stop a `T`-coalition completely (the coalition cannot unpause), which D2 alone could not; worth stating in §3.3(1) once F4's expiry is added.
- **Pause on BSC only by signed message**: removes the need for the signer key to hold BNB and keeps the pauser identity verifiable; the 1-hour deadline (L6) bounds replay.
- **Per-claim cap on burns** (`net ≤ dailyCap`): guarantees every recorded withdrawal is payable within one window; consistent with `executeQueued`'s "lowered cap" exception.
- **Worked scenarios §16.1 arithmetic** checks out (conversion 99.85 CS and 499.45 CS, Carol 289.75 csUSDT, Bob 11.99, fund 0.36, vault 400.05 = circulation 400.05, gas pool 0.00018 BNB), apart from items 17–19 above.
- **Glossary** is accurate on the bond, exit, pause/full pause, band and gas pool rules apart from items 15–16.
